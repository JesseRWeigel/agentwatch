agentwatch

Every agent session on the machine, found in the process table. Not the ones an orchestrator launched, and not the ones that registered themselves somewhere. All of them, including the one you started by typing claude in a terminal an hour ago and forgot.

Why a session and its log are hard to join

A running process gives you a pid and a working directory. The interesting state is in a JSONL log under a directory named after that working directory with the slashes replaced. Two things go wrong.

The naming rule is not one rule. On the machine this was written on, of 61 project directories that record a working directory, 59 follow "/" → "-" and 2 also map "." → "-". Both conventions sit on the same disk, because a directory is created by whichever version was running at the time and is never migrated. The rule is also lossy in every version: /a/b and /a-b produce the same name, so even a perfect implementation cannot be inverted. So the directory name is a hint, and the working directory recorded inside the log decides.

Two agents in one repository is normal. When several logs fit, this says so. It does not pick the most recently modified one and present it as a fact, because a reader cannot tell a confident answer from a coin flip, and the button next to the answer sends SIGTERM.

3 of 6 are certain, 2 are ambiguous, and 1 is a process whose details this user may not read. That last one still gets a row: "nothing is running" and "something is running that you are not allowed to look at" must not print the same board, and the second is exactly when somebody is hunting for missing CPU.

Correlating everything at once beats correlating each alone

A log belongs to one session. When one process names its session on its command line, it claims that log, and a rival sharing the directory is then left with exactly one candidate. That turns a coin flip into an answer without guessing. It came from a real pair of sessions in one directory where the second was being reported as a choice between two logs, one of which was already spoken for.

One inference, marked as one

Nothing in a session log says "waiting for you to approve a tool call". What it says is that a tool was requested and no result has been written. That is also what a tool call looks like for its first few seconds, so the only thing separating a running test suite from a permission prompt nobody is looking at is how long it has been true.
